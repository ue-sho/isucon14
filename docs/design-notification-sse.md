# 通知エンドポイントのSSE化設計

本PRでNode.js単一プロセス向けのSSE実装を追加。ローカルMySQLで動作検証済み。s1へのデプロイと競技ベンチによる性能比較は未実施。

## 目的と根拠

`docs/ISURIDE.md` の通知仕様に従い、利用者・椅子向け通知をSSEに置き換える。繰り返し発生するHTTPリクエスト、認証、状態変更のないDB読み取りを減らす。

既存ログではapp通知9,287回・合計1,185.587秒、chair通知11,243回・合計1,177.589秒。COMMITは28,389回・75.9416秒でSQL時間の57.6%。これらは変更前の別ブランチの記録であり、SSEの効果は未計測。

SSEの接続時間はalpの処理時間として長く見えるため、移行後のSUMやAVGを従来のJSONレスポンスと直接比較しない。スコア、通知遅延、SQL回数、CPU、メモリを主な評価軸にする。

## 守る契約

- 同じURLとCookie認証を使い、Content-Typeを `text/event-stream` にする。
- 本文は `data: <既存dataフィールドのJSON>\n\n`。retry_after_msは含めない。
- 接続直後に未送信の最古状態を返す。残りを順番に送信し、未送信がなければ最新状態を返す。最新だけを先に送って過去の遷移を追い越さない。
- ライドをまたいでも未送信状態を省略しない。利用者は自分のライド、椅子は自分に割り当てられたライドだけを取得する。
- ライドがない場合は `data: null\n\n` を直ちに返す。クライアントとの互換性を結合テストで確認する。
- 状態変更から3秒以内の通知を目標にする。通常はコミット直後、通知イベント欠落時も定期照合で復旧する。

## 構成

新規モジュールを次の責務に分ける。

| モジュール | 責務 |
| --- | --- |
| db.ts | 既存poolをmain.tsから抽出し、短時間の接続取得・解放を提供 |
| notification_repository.ts | 所有者を限定した未送信履歴、最新状態、レスポンス材料の取得、送信記録 |
| notification_stream.ts | 宛先別の購読、dirtyフラグ、排他実行、共有照合、SSE送信、JSON互換経路 |
| notification_lifecycle.ts | 初期化中の受付停止、通常リクエストとストリーム処理の終了待ち |
| notification_payload.ts | 既存の料金・椅子統計計算を使う通知本文の構築 |

プロセス内イベントは「DBを再確認するきっかけ」として使う。業務状態の正本は `rides` / `ride_statuses`、通知順序と再接続時の復旧元は以下の通知履歴テーブル。イベント自体に履歴を蓄積しない。

接続ごとに30msのDBポーリングを実行しない。共有タイマーを1秒ごとに動かし、接続中の宛先をまとめて照合する。未送信履歴がある宛先だけ本文を構築する。照合SQLは128宛先ずつに分けて順次実行し、DB処理の同時実行数は既存poolで制限する。1秒周期だけで3秒以内を保証できるわけではなく、照合待ちと送信待ちを含めて測る。

## DB接続と認証

現在のmain.tsは全リクエストで接続を取得し、finallyでrollback・解放している。ストリーム開始後にこの接続を使わない設計にする。通知専用ルートは通常APIのDBミドルウェアから分離する。

通知専用認証でpoolから接続を借り、Cookieを検証し、user/chairの必要な値をコピーして直ちに解放する。その後にストリームを開始する。履歴取得・送信記録はそれぞれ短時間の接続を使う。ネットワーク書き込みを待つ間にトランザクションやDBロックを保持しない。

導入済みHonoのstreamingヘルパーは書き込みエラーを吸収するため、TransformStreamのwriterを直接使い、書き込み失敗と2秒の送信待機タイムアウトを検出する。Nodeアダプターによる切断時のabort伝播はHTTP結合テストで確認した。既存のctx.var.dbConnを非同期ストリームから参照しない。

## 接続と送信の流れ

1. 認証後、宛先単位の購読を登録してからDBを読む。登録前に読み出してイベントを取りこぼす競合を避ける。
2. 宛先の送信処理を直列化する。同じ宛先への重複接続は新接続を優先し、旧接続の処理が停止してから新接続を開始する。
3. dirtyを落として、未送信の履歴を取得する。ライドのcreated_at/id、状態のcreated_at/idの順で安定して並べる。同時刻の扱いは状態遷移を作る処理と整合させ、順序テストで確認する。
4. 最古から1フレームずつ書き込みをawaitする。成功した状態だけ送信日時を記録する。送信記録は既に記録済みなら変更しない条件付きUPDATEとする。
5. 初回に未送信履歴がなければ最新状態を1回送る。送信中にdirtyになった場合は、待機せずもう一度DBを読む。
6. dirtyでなくなったらイベントを待つ。接続解除時には購読・待機処理を必ず破棄する。

非同期処理の途中で起きたイベントでdirtyが失われないよう、実行中とdirtyを別管理する。DB取得の各回は新しいスナップショットを使い、長寿命のREPEATABLE READトランザクションにしない。

## 再接続と送信保証の限界

送信前にsent_atを更新すると欠落するため、必ずフレーム書き込み後に記録する。書き込み成功後・記録前の切断やプロセス停止では再送を許容する。送信記録に失敗したらその接続の処理を停止し、後続状態を追い越して送らない。

ただし「サーバーの書き込み成功」は「クライアントが受信して処理済み」の確認ではない。sent_atだけで、任意の通信断に対する厳密なat least onceは保証できない。前提となるクライアントのACKが仕様にないため、この限界は既存JSON方式にもある。

Last-Event-IDの利用は初版の必須条件にしない。配信済み状態に対応するIDを使って再開できる拡張は可能だが、ベンチクライアントがIDを保存・再送するかを確認する必要がある。配布フロントには初回fetch後に別途EventSourceを作る処理もあり、すべての再接続でカーソルが来るとは仮定できない。初回フレームはdataで始め、追加フィールドを先頭に置かない。

初版はDBの未送信履歴を再取得し、未送信がなければ最新状態を再送する。通信断で記録済みフレームをクライアントが受信できなかったケースを結合テストに含める。厳密な受信保証まで求める場合は、クライアントの再開カーソルまたはACKを含めた追加設計を要する。ベンチ成功だけを厳密な配送保証の証明にしない。

## 状態更新側の変更

通知はSQL実行時点ではなく、トランザクションのcommit成功後に起こす。ロールバックした状態を送信しない。

| 更新元 | 状態・変更 | 起こす宛先 |
| --- | --- | --- |
| appPostRides | ライド作成 / MATCHING | user |
| internalGetMatching | chair_id割り当て | user、割り当てたchair |
| chairPostRideStatus | ENROUTE / CARRYING | user、chair |
| chairPostCoordinate | PICKUP / ARRIVEDが実際に追加された場合 | user、chair |
| appPostRideEvaluatation | 評価 / COMPLETED | user、chair |

マッチングのUPDATEは現在autocommitなので、その完了後に起こす。椅子が付く前のMATCHINGも、割り当て後に椅子へ送る。状態が変わらない通常の座標更新では通知を起こさない。

コミット直後のプロセス停止などでイベントが欠落しても、DB履歴を定期照合するため次回に復旧する。単一プロセスを前提にし、複数プロセスへ拡張するときは共有通知手段か全プロセスのDB照合が必要。

## テーブル変更を含む採用案

ライドをまたぐ配信順序を明示するため、業務状態の更新と同じトランザクションで宛先別の通知履歴を追加する方式を採用する。以下はDDLの設計案。実装前に初期データ量と実行計画を確認する。

```sql
CREATE TABLE notification_streams (
  recipient_type ENUM('app', 'chair') NOT NULL,
  recipient_id VARCHAR(26) NOT NULL,
  last_seq BIGINT UNSIGNED NOT NULL DEFAULT 0,
  written_seq BIGINT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY (recipient_type, recipient_id)
);

CREATE TABLE notification_events (
  recipient_type ENUM('app', 'chair') NOT NULL,
  recipient_id VARCHAR(26) NOT NULL,
  seq BIGINT UNSIGNED NOT NULL,
  ride_id VARCHAR(26) NOT NULL,
  ride_status_id VARCHAR(26) NOT NULL,
  status ENUM('MATCHING', 'ENROUTE', 'PICKUP', 'CARRYING', 'ARRIVED', 'COMPLETED') NOT NULL,
  created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (recipient_type, recipient_id, seq),
  UNIQUE KEY uq_notification_status
    (recipient_type, recipient_id, ride_status_id)
);
```

`written_seq` はフレーム書き込み後にDBへ記録した位置であり、クライアントのACKではない。前述の通信断時の保証限界はテーブルを追加しても変わらない。

### 書き込みと順序

状態追加と同じトランザクションで宛先のnotification_streams行をロックし、last_seqを増やしてnotification_eventsを追加する。宛先が複数ならapp、chairの順にロックする。ロールバック時には連番と履歴も戻る。グローバルAUTO_INCREMENTやULIDの大小をコミット順序とはみなさない。

同じライドの状態追加はrides行をロックして直列化する。ロック順は「rides行 → app stream行 → chair stream行」に統一し、既存の座標更新・評価・マッチング・状態更新の全経路で確認する。DBエラー時は既存のハンドラーでトランザクション全体をrollbackしてエラーを返す。決済を含む処理の無条件な自動再試行は追加しない。

ライド作成時にはappにMATCHINGを追加する。椅子割り当てをトランザクション化し、chair_id更新と、その時点までの履歴をchair宛てに追加する。以降の状態変更では両宛先に追加する。割り当て済みrideのMATCHINGを椅子側から落とさない。uq_notification_statusにより同じ状態履歴の二重登録を防ぐ。

同一宛先ではこのロックで確定したseqを配信順にする。時刻の同値や複数ライドの並びを読み取り時のソートに頼らない。異なる宛先間に共通の配信順序は要求しない。

### 読み取りと送信記録

認証済み宛先について `WHERE recipient_type = ? AND recipient_id = ? AND seq > ? ORDER BY seq LIMIT 64` で取得する。先の接続フローにある時刻順の履歴取得をこのseq順取得に置き換える。取得範囲の末尾まで処理したら続きへ進む。

共有の1秒照合では、接続中の宛先のstreams行だけをまとめて読み、last_seq > written_seqの宛先を起こす。すべてのride_statusesや全利用者の履歴を走査しない。DBイベント追加後のプロセス内通知はあくまで高速化で、永続化済みイベントを正とする。

フレーム書き込み後、短いトランザクションでwritten_seqの前進と、対応するride_statusesのapp_sent_at / chair_sent_atを更新する。途中失敗時は両方戻し、その接続の送信を止める。seqの飛ばし更新を禁止し、同一宛先の送信処理は一つにする。再接続時は旧処理の停止を待ち、記録済み位置の次から再開する。未送信イベントがなければlast_seqのイベントを最新状態として再送する。

chair_sent_atはマッチングの `COUNT(chair_sent_at) = 6` 判定に使われるため維持する。COMPLETED送信後の記録が確定するまで椅子を再利用しない。マッチング方式自体の変更は今回に含めない。

### 本文

通知履歴には順序と状態の識別情報を保存し、fare、chair stats、座標、利用者名などは配信時に必要なライドから構築する。状態はイベント行から読み、最新状態で上書きしない。これによりMATCHINGからCOMPLETEDまでの遷移を維持しながら、評価や椅子割り当てなどの関連情報は既存レスポンスの意味を保つ。

初版ではfareとstatsの既存計算を再利用し、通知が必要なときだけ実行する。接続維持やheartbeatでは計算しない。統計キャッシュの導入は別の改善単位にする。

### 初期化・既存データ・互換性

実際の初期化経路は `POST /api/initialize → bash ../sql/init.sh → 1-schema.sql → 2-master-data.sql → 3-initial-data.sql.gz`。既存テーブルは1-schema.sqlでDROP/CREATEされるため、新テーブルも毎回DROP/CREATEする。初回デプロイ時だけのDDLや、前回ベンチのメモリ・カーソルを引き継ぐ構成にはしない。

採用する実行順序は次のとおり。

1. initializeを排他実行し、通知hubと通常の状態更新API・内部マッチングの新規受付を停止する。処理中の書き込みと通知処理を終了させ、DB接続・トランザクションを解放する。通知だけを停止してもDDLと業務更新が競合するため、更新側も対象とする。
2. SSE接続を閉じ、hubの購読・dirty・タイマー・カーソルを破棄する。終了待ちに成功するまでDDLへ進まず、旧接続の非同期処理が残ったまま再開しない。
3. init.shで業務テーブルと新通知テーブルを再作成し、マスタ・初期データを投入する。
4. 新しい `4-notification-data.sql` で投入済みデータから通知履歴・送信位置を再構築する。空テーブルのまま通常受付へ進まない。
5. payment_gateway_urlを設定し、通知履歴と送信位置の整合性を確認する。
6. hubの受付と定期照合を再開し、通常受付を再開してからinitialize成功を返す。

現行init.shは `set -eux` でgzipとmysqlをパイプ接続している。拡張時にpipefailを有効にし、展開・投入・通知履歴構築のいずれの失敗もinitialize失敗へ伝える。DDLは暗黙コミットされるため、初期化全体をrollback可能とは扱わない。失敗時は受付停止を維持し、次のinitializeで再度DROP/CREATEから復旧できるようにする。ENV=local-devでは現行init.shが何もせず終了するため、開発用にも明示的なDB準備手順を用意し、通知テーブルの存在を確認する。

競技マニュアルのinitializeタイムアウトは**30秒**。既存データ投入、通知履歴構築、処理終了待ちを含めてこの範囲に収める。通知履歴構築はNode.jsから1件ずつINSERTせず、宛先別の連番を付ける一括SQLで行う。時間内に収まらない場合は全履歴複製を見直し、送信済み履歴の省略と最新状態の別取得を検討する。その場合も未送信履歴とchair_sent_atに基づくマッチングの意味を維持する。

1-schema.sqlに新テーブルを定義する。初期データ投入後に通知履歴を構築する初期化SQLを追加し、init.shから実行する。過去データについてもapp/chair双方の送信日時を参照する。宛先別のライド・状態履歴から順序を決定し、送信済み履歴を含めてseqを割り振る。written_seqは連続して送信済みとなっている範囲の末尾とし、途中に未送信があればそこから再送する。初期データに同時刻の状態がある場合は状態遷移の順序を優先して並べる。

ベンチのinitializeで毎回再現することを必須とする。初期化時間・テーブルサイズも計測し、過大なら過去の完了済みライドをどこまで保持するかを別途評価する。初版は履歴の削除を行わない。

JSONへ切り戻した場合も同じnotification_eventsを読み、1回1件を返して同じ送信記録を行う。従来の「最新rideだけを見る」実装へ切り替えてカーソルの意味を崩さない。既存のポーリング間隔変更はこのJSON互換経路にのみ適用する。

## nginx、切断、初期化

両通知URLに専用locationを設け、proxy_bufferingをoff、proxy_cacheをoffにする。アプリからもCache-Control: no-cacheとX-Accel-Buffering: noを返す。proxy_read_timeoutは60秒以上とし、15秒ごとのSSEコメント `: heartbeat\n\n` で無通知時にも通信を維持する。初回のdataフレームより先にはコメントを送らない。

書き込みの待機時間に上限を設け、遅い接続は切断する。プロセスメモリに無制限の送信キューを作らず、残りの履歴はDBに残す。タイマー、接続数、dirty宛先数、送信待ち時間を計測する。

/api/initialize開始時に通知受付を停止し、既存接続を閉じ、新規通知接続を一時的に止める。進行中の通知DB処理を終了させてからinit.shを実行する。終了待ちが失敗した場合はDDLを実行せず受付停止を維持し、旧処理が新DBへsent_atを書き込む競合を防ぐ。初期化成功後にhubを空の状態で再開する。失敗時は通知を再開せずinitializeをエラーにする。送信待ちがDB初期化を無期限に妨げないように切断を先に行う。

## 実装・検証の順序

1. 新テーブルと初期化処理を追加し、全状態更新を通知履歴と同じトランザクションにする。DB接続管理と履歴取得を分離する。ライドをまたぐ未送信履歴、同時刻の順序、アクセス制御をテストする。
2. hubと両SSEルート、全更新元のcommit後通知、nginx設定を追加する。
3. 接続直後の状態、MATCHINGからCOMPLETEDまでの順序、ライドAの末尾からBへの遷移を確認する。
4. 読み出し中の更新、ロールバック、重複接続、低速接続、送信記録失敗、再接続、通知イベント欠落、初期化を確認する。initializeを連続2回実行し、途中失敗後の再実行・旧接続からの書き込み阻止・前回ベンチの履歴消去・30秒以内の完了を確認する。大量SSE接続中も通常API用DB接続が使えることを確認する。
5. TypeScript型検査、ベンチのSSE受信実装確認、実機のフレーム即時到着確認を行う。
6. 稼働ブランチとの関係を整理したうえで同一条件のJSON基準ベンチとSSEベンチを実行する。解析処理と負荷生成を重ねない。

採用条件はベンチ成功、状態遷移の欠落なし、通知遅延3秒未満、SQL回数の削減、スコア改善。SQL回数は総数と完了ライド当たりの両方で比較し、接続数とメモリの増加も確認する。未達なら同じDB履歴を使うJSON方式へ戻せるよう、移行中は環境変数でJSON/SSEを切り替える。DBスキーマ変更は両方式と互換性を保つ。


## 実装の利用・検証方法

既定はSSE。Nodeプロセスの環境変数 `NOTIFICATION_TRANSPORT=json` を設定して再起動すると、同じ通知履歴・送信位置を使うJSON方式へ切り替わる。デプロイ後は `/api/initialize` で新テーブルと初期通知履歴を作成してから動作確認する。サーバー再起動だけで新テーブルは作成されない。

通常検査は `cd webapp/nodejs && npm run typecheck && npm test`。MySQLを使う結合テストは明示的に指定した場合だけ動く。使い捨てのローカルMySQLに `isuride` データベースとアプリ用ユーザーを用意し、`ISUCON_DB_PORT=13316 SSE_TEST_MYSQL=1 npm test` を実行する。このテストは対象DBを初期化する。ホストは127.0.0.1、ポートは3306以外に限定し、HTTPテストサーバーには18081番を使う。

検証結果: MySQL 8.0コンテナとNode.js v24.12.0で結合テスト13件・ライフサイクル単体テスト2件（計15件）が成功。TypeScript型検査、変更ファイルのBiome検査、init.shの構文検査、ローカルnginxコンテナによる設定全体のnginx -tも成功。
