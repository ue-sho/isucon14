# オーナー走行距離集計の読み取り改善

## 対象と変更

2026-10-24。master `5438e7f` から `perf/owner-distance-covering` を作成。
対象は `GET /api/owner/chairs`。master には対象オーナーへの絞り込みと
`chairs(owner_id)` のインデックスが既に入っている。

- 緯度・経度の `LAG` に共通の名前付きウィンドウを使う。MySQL の実行計画で
  2回あった Window aggregate が1回になり、中間の一時テーブルを1つ削減する。
- 既存の `chair_locations(chair_id, created_at)` インデックスの末尾に
  `latitude, longitude` を追加する。集計に必要な列をインデックスから取得し、
  履歴テーブル本体へのアクセスを省く。先頭2列は維持する。
- 距離の定義、履歴、取得時刻、APIレスポンスは維持する。
  座標更新ハンドラーとMySQL設定は変更しない。

インデックス変更は `webapp/sql/1-schema.sql` に定義し、初期化で再現する。
インデックスの容量・更新負荷は増えるため、座標更新の担当者との統合後に
座標更新の応答時間も比較する。

## 独立したローカル検証

専用の MySQL 8.0 Docker コンテナを使用。本番DB・サービスへの変更なし。
100椅子・5オーナー、49,500位置履歴を作り、20椅子を持つオーナーを対象にした。
対象履歴は9,500行。両条件で ANALYZE TABLE を実行して統計を更新し、
同一SQLの EXPLAIN ANALYZE の先頭ノードの終了時間を各7回計測した中央値。
キャッシュが温まった状態で順に計測した参考値で、競技ベンチではない。

| 条件 | SQL実行時間の中央値 |
| --- | ---: |
| master | 47.3ms |
| 共通ウィンドウのみ | 32.4ms |
| 共通ウィンドウ + カバリングインデックス | 27.5ms |

この条件では約42%短縮。変更後は位置履歴が Covering index lookup になり、
ウィンドウ処理が1回になった。

変更前後の全レスポンス列が一致することを確認。
位置履歴なし、負座標、同一地点の連続記録、往復を含むデータを用い、
距離を別途Pythonで計算して全対象椅子の結果と照合した。
履歴なしでは距離0・更新日時NULL、その他では最新の履歴時刻を返すことも確認。
TypeScript型検査と git diff --check を実施。
