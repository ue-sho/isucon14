# 最新座標・累積移動距離の保存

2026-10-24、`codex/chair-location-state`。基準コードは `3c9b927`。位置履歴から owner/chairs の応答ごとに距離を再集計する処理を、新テーブルの参照へ切り替える。共有サーバーへの反映と競技ベンチは未実施で、性能効果は未確定。

## 変更

- `chair_locations` に受理した位置履歴を残す。
- `chair_location_state` に椅子ごとの最新座標、最後の記録日時、累積移動距離を保存する。
- 椅子登録時に初期状態行を作り、登録自体と同じトランザクションで確定する。
- coordinate は先に既存の rides 行をロックし、状態行を `UPDATE` してから履歴を追記する。状態行の更新ロック下で前座標との差分を加算するため、並行更新でも加算を取りこぼさない。
- 初回の距離加算は0、同じ位置の再報告は距離を増やさず記録日時を更新する。往復は両方向の移動距離を合計する。
- 記録日時は DB 内で `max(現在時刻, 前回時刻 + 1マイクロ秒)` とし、同時刻の報告や時計の巻き戻りでも椅子ごとの順序を保持する。履歴へは `INSERT ... SELECT` で同じマイクロ秒精度の日時をコピーする。
- 位置履歴、状態行、PICKUP / ARRIVED の状態履歴、通知イベントを同じトランザクションで確定する。
- owner/chairs は状態行を JOIN する。近隣検索・配車・通知送信の方式は変更しない。

## 初期化

`init.sh` は参照データと通知データを読み込んだ後に `5-chair-location-state.sql` を実行する。この SQL は位置履歴を `(created_at, id)` 順に集計し、最新座標と累積距離を復元する。履歴を持たない椅子もNULL座標・日時、距離0で作成する。

再構築はトランザクション内の DELETE / INSERT で行い、繰り返しても距離を二重加算しない。稼働中に実行せず、初期化のリクエスト停止中か、アプリの書き込みを停止した移行時にのみ使う。

状態行が欠けたまま coordinate が呼ばれた場合は失敗させる。履歴がある椅子を距離0から再開させるような、自動的な空行作成は行わない。

## 共有環境を使わない動作確認

Docker と Node.js、`webapp/nodejs` の依存パッケージを用意し、リポジトリのルートで実行する。

```bash
bash scripts/test-location-state.sh
```

このスクリプトは次の順で実行する。

1. 固有名の一時 MySQL 8.0 コンテナを作成する。データ領域は一時コンテナ専用で、ホストの既存 DB データをマウントしない。SQL ソースだけを読み取り専用でマウントする。
2. 127.0.0.1 の動的ポートで接続し、コンテナ内だけで実際の `init.sh` を2回実行する。各回がアプリ側の25秒制限以内か確認する。
3. 新しいランダム名のテスト DB で、実際の coordinate・owner/chairs ハンドラーを検証する。
4. 既存の近隣検索、SSE 通知、初期化ライフサイクルのテストも実行する。SSE テストの MySQL クライアントは一時コンテナ内への実行に固定し、既存の DB 接続環境変数を使わない。
5. 終了時に自分が作成したコンテナと一時ファイルだけを削除する。

新設テーブルのテストは、参照データの位置履歴21,209行から JavaScript で独立に距離を計算し、全500台の保存値と照合する。履歴なしの113台、初回・同一座標・負座標・往復、並行12更新、固定した DB 時刻での順序、owner の所有者絞り込み、近隣検索への反映、登録失敗、COMMIT前の失敗、通知作成失敗時の全体ロールバック、状態行欠落後の復元も確認する。

この手順は s1 / bench への SSH、`task deploy`、`task bench`、Discord 投稿を行わない。ローカルでは一時アプリが TCP 18081 を使用するため、他のプロセスが使用していない状態で実行する。

### 実施結果

ローカルの MySQL 8.0.46 で、位置情報9件、既存SSE通知13件、近隣検索5件、初期化ライフサイクル2件の **計29件が成功**（失敗・スキップなし）。参照データ全500台の保存値を照合できた。コンテナ内の実 `init.sh` は2回とも約1秒で完了した。この時間はローカル環境の値であり、s1 の初期化時間を保証するものではない。

`npm run typecheck`、`bash -n`（テストスクリプト・初期化スクリプト）、`git diff --check` も成功した。作成した一時コンテナは削除済み。s1 のデータ・設定・稼働状態は変更していない。

## 計測・反映時の注意

- ローカルの正しさの確認と、競技ベンチでの性能確認を分ける。owner の再集計を省く代わりに coordinate の書き込みが1件増えるため、性能向上は保証しない。
- binlog とアプリ・スキーマの他の変更を固定し、導入前後で成功可否、スコア、coordinate の平均・P95、owner/chairs の応答時間、COMMIT 平均、書き込み量を比較する。
- **`task deploy` だけでは新しいテーブルや初期集計行は作られない。** 初回導入は新スキーマの準備とアプリ切替を合わせる必要がある。
- ベンチの初期化を使う場合は DB リセットを伴う。チームで時間を合わせてから実施する。既存データを残す移行では、アプリの書き込みを停止し、新テーブルだけを作成して再構築 SQL を実行した後に新実装を起動する。`1-schema.sql` 全体は既存テーブルを削除するため、データ保持を目的とする移行には使わない。
- MySQL の設定検査や競技ベンチ成功を、ローカルテストの結果から推定しない。
