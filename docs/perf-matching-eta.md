# 迎車距離とモデル速度を考慮した配車

## 対象と仮説

2026-10-24。master `1275052` から `perf/matching-eta` を作成し、
実装中に更新された最新master `0c29d2e`（PR #15）も取り込んだ。
対象は `GET /api/internal/matching`。
masterには走行距離集計のPR #13もマージされており、その状態を起点とする。

従来は稼働中の椅子をランダムに選び、空き確認を最大10回繰り返す。
近さ・速度を考慮しないため迎車が長くなり、空き椅子があっても10回とも
使用中の椅子を引くと割り当てできない。仕様にはモデル速度を考慮した
割り当てが推奨されている（docs/ISURIDE.md）。

## 変更

- 最も古い未割り当てライドを優先する。1回の呼び出しで最大16回、
  または開始から200ms経過まで配車を繰り返す。空き椅子・依頼がなければ終了。
  各ライドを個別トランザクションで確定し、呼び出し終了時に通知を起こす。
- 稼働中かつ空いている椅子をSQLで抽出し、最新座標から乗車地点までの
  マンハッタン距離をモデル速度で割った推定迎車時間の昇順で1台選ぶ。
- 推定時間が同じなら椅子ID順に選ぶ。位置不明の椅子は既知位置の椅子より後にする。
  全台位置不明の場合も従来同様に配車可能とし、未知モデルの速度は1として扱う。
- 空きの条件は従来の割り当て直前チェックと同じで、過去の全ライドについて
  椅子宛て通知済み状態が6件であること。完了通知の未送信中に次のライドを割り当てない。
- ライド、椅子の順にロックし、ライドの割り当て、椅子の稼働・空きを再確認する。
  競合した場合はロールバックし、次回呼び出しで再選択する。
- 既存の通知履歴登録とコミットを維持する。
- 座標更新・通知ハンドラー・スキーマ・MySQL設定には変更なし。

## 実行計画

専用のローカル MySQL 8.0.46 で500椅子、35,000位置履歴、2,100ライドを作成。
各椅子に完了・通知済みの過去ライド4件、100椅子には追加の使用中ライドを作った。
全椅子を稼働中とし、モデル速度2と7を混在させた。

最初の候補SQLでは最新位置のIDを相関サブクエリで求めて主キー結合したが、
EXPLAIN ANALYZE で位置検索が1,500回、各70行のソートになり、中央値39.3msだった。
LEFT JOIN LATERAL に変更し、固定値の chair_id も含む
`ORDER BY chair_id DESC, created_at DESC LIMIT 1` を使うと、
既存インデックスの逆順検索で1行だけ読む計画になった。
この条件で候補SQLの中央値は12.3ms（各5回）。
これらは開発中SQL同士の比較であり、従来のランダム選択SQLより速いという意味ではない。

3つの乗車地点について、選択された椅子が独立したPython計算での推定迎車時間の
最小値と一致することも確認した。移動経路・通知・API待ちを含む実迎車時間や
競技スコアの改善は未確認。

## 検証

- TypeScript型検査、git diff --check。
- 専用MySQLで配車統合テスト11件：速度と距離の比較、最新座標、停止中・使用中・
  完了通知待ちの除外、通知済みの椅子の再利用、古い依頼の優先、位置やモデルが不明な場合、
  空きなし、候補選択後の稼働・空きの変化、同時実行時の二重割り当てと通知重複の防止、複数件配車、
  バッチ上限と次回呼び出しへの継続。
- 同じ専用MySQLで既存SSE通知統合テスト13件。配車後のMATCHING通知、
  状態遷移、ロールバック、再接続、初期化を含む。

配車テストは `MATCHING_TEST_MYSQL=1` を付けて
`node --import tsx --test test/matching.test.ts` で実行する。
データを初期化するため、ISUCON_DB_HOSTにはloopback、ISUCON_DB_PORTには
専用MySQLの3306以外のポートを必ず指定する。
SSEテストは別プロセスで `SSE_TEST_MYSQL=1` を付けて実行する。
両テストは同じDBに対して同時に実行しない。

## 初回ベンチ失敗と修正

`57bdb82` のユーザー実行ベンチは `pass=false`、スコア5071、
種別エラー数 `map[5:2 17:2 26:1 32:1]`。
94.0%がマッチング待ち、19.0%が迎車、0.0%が実移動時間に不満。
17:41:48 JSTに「ライドが長時間マッチングされませんでした」で終了した。

同じログの候補SQLは196回・合計0.4819秒・平均2.5ms。
配車依頼は226件、終了後DBには未配車96件が残っていた。
matcherは0.5秒sleepを挟む直列呼び出しで、初版の1回1件という実装では
理論上でも毎秒2件未満に制限される。迎車改善で依頼が増えた際に
処理量が不足する可能性が高いため、上記の上限付きバッチ配車に修正した。
修正後の配車統合テスト11件は成功。
