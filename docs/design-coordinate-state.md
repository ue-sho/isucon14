# coordinate の調査と DB 再設計案

2026-10-24。この文書の依頼範囲は調査・設計案まで。テーブル新設の実装・SQL 実行・デプロイはしていない。binlog 設定変更は別の変更としてユーザーが進めている。

## 結論

位置情報を「履歴」と「現在の状態・計算結果」に分離する。`chair_locations` は履歴として残し、椅子ごとに最新座標と累積移動距離を保持する `chair_location_state` を新設する案を推奨する。

これにより owner/chairs の履歴全件集計を除去できる。nearby-chairs も最新座標の取得を JOIN に置き換えられる。ただし coordinate は現在、距離計算をしていない。集計テーブルへの書き込みを追加するだけでは coordinate の高速化は保証できず、書き込み負荷が増える可能性もある。coordinate 自体の短縮には、COMMIT 待ちの原因調査と、ライド・ステータス照会の削減を別途評価する。

## 初回調査時の実装

### coordinate

`webapp/nodejs/src/chair_handlers.ts:58` の処理は以下。

1. ミドルウェアで `chairs.access_token` を検索して認証。
2. トランザクションを開始し、`chair_locations` に座標を INSERT。
3. 椅子の最新ライドを `ORDER BY updated_at DESC LIMIT 1 FOR UPDATE` で取得。
4. ライドがあれば `ride_statuses` から最新ステータスを取得。
5. 乗車地点への到着なら ENROUTE → PICKUP、目的地への到着なら CARRYING → ARRIVED。状態遷移時は履歴と通知イベントも同じトランザクション内で作成。
6. INSERT した座標行を再 SELECT して DB の記録日時を取得し、COMMIT 後に `recorded_at` を返す。

距離計算は coordinate にはない。完了済みライドしかない場合も、最新ライドのロックとステータス取得は行われる。

### 距離と最新座標の参照

- `owner_handlers.ts:104`: オーナーの椅子に絞った履歴に対し、`LAG` → マンハッタン距離 → `SUM` / `MAX(created_at)` を毎回実行。オーナーによる絞り込みは既にあるが、履歴が増えるほど再集計が重くなる。
- `app_handlers.ts:471`: 全椅子を取得し、稼働中の各椅子について過去ライドとステータスを確認。その後 `chair_locations` から最新1件を取得する N+1 構成。
- `internal_handlers.ts`: 配車は現在ランダム選択で、座標を利用していない。最新座標テーブルを追加しただけでは配車品質は変わらない。
- 既存インデックス: `chair_locations(chair_id, created_at)`、`rides(chair_id, updated_at)`、`ride_statuses(ride_id, created_at)`。単なる同等インデックスの追加を優先する根拠は薄い。`chairs(owner_id)` は未定義。

## 推奨するテーブル構成

| テーブル | 用途 | 更新の契機 |
| --- | --- | --- |
| chairs | 所有者、名称、モデル、認証、稼働設定 | 登録・稼働設定変更 |
| chair_locations | 受理した座標履歴。再計算・照合の根拠 | coordinate ごとに追記 |
| chair_location_state（新設） | 最新座標、記録日時、累積移動距離 | coordinate ごとに同一トランザクションで更新 |

DDL の設計例（未実行）。位置未登録の椅子も1行持つ。

```sql
CREATE TABLE chair_location_state (
  chair_id VARCHAR(26) NOT NULL,
  latitude INT NULL,
  longitude INT NULL,
  recorded_at DATETIME(6) NULL,
  total_distance BIGINT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY (chair_id)
);
```

`chairs(owner_id)` は現在のスキーマに追加済みなので、重複して作成しない。

最新座標と累積距離は同じ受理イベントから更新するため、最初は同じ行にまとめる。別々の最新座標・距離テーブルに分けると書き込みと整合性管理が増える。`chairs` に直接追加する方法もあるが、認証や稼働設定と座標の高頻度更新を分けるため別テーブルを選ぶ。

`recorded_at` は「最後に座標が報告された日時」。同一座標が再報告されても更新する。これを owner API の `total_distance_updated_at` に使い、既存の `MAX(created_at)` と意味を合わせる。未報告なら距離0、座標・日時NULLとし、近隣検索には出さない。

### 更新処理の設計

1. 椅子登録時に chairs と初期状態行を同じトランザクションで作成する。
2. coordinate のトランザクションで、現状と同様に対象ライドをロックする。続いて `chair_location_state` を主キーで `FOR UPDATE` 取得し、同じ椅子への更新を直列化する。
3. 前座標との差 `abs(new_lat - old_lat) + abs(new_lon - old_lon)` を計算する。初回の加算は0。最初の座標を原点からの距離として数えない。
4. 行ロック取得後に DB 時刻を一度取得し、その時刻を履歴の `created_at`、状態行の `recorded_at`、応答の `recorded_at` に共通使用する。履歴 INSERT 後の SELECT は不要になるが、時刻取得用 SELECT が残るので、これ単独では問い合わせ数削減と数えない。
5. 履歴 INSERT、状態行の座標更新と距離加算、必要なライド状態遷移・通知イベントを同じトランザクションで確定する。失敗時はすべてロールバックする。
6. COMMIT 成功後に応答し、既存の通知起床処理を通す。

計算用の前座標取得から累積値更新までをロック内に置く。ロックなしの read-modify-write は距離加算の取りこぼしを起こす。並列書き込みでも受理順序と履歴時刻が逆転しないようにする。同一椅子の時刻が同値になり得る環境では、履歴順序を明確にする連番などを追加し、初期集計と照合でも同じ順序を使う。ULID の辞書順を無条件に受理順とはみなさない。

既存のライド状態更新は rides 行を先にロックする。新テーブルから rides / chairs を逆順で取りにいく処理を増やさず、通知を含めたロック順を実装時に統一する。

### 読み取りの変更

owner/chairs は次の JOIN に置き換える。SQL は設計例。

```sql
SELECT c.id, c.name, c.model, c.is_active, c.created_at,
       COALESCE(s.total_distance, 0) AS total_distance,
       s.recorded_at AS total_distance_updated_at
FROM chairs c
LEFT JOIN chair_location_state s ON s.chair_id = c.id
WHERE c.owner_id = ?;
```

nearby-chairs は、現在の一括取得 SQL のうち最新座標を履歴から引く相関サブクエリを、状態テーブルとの JOIN に置き換える。`is_active = TRUE`、位置登録済み、マンハッタン距離の条件、未完了ライドを除外する `NOT EXISTS` は維持する。最初から空車判定やライド状態の保存方法まで変える必要はない。

検索原点が毎回変わる「利用者から椅子までの距離」は永続化しない。保存する計算結果は、座標履歴に対して一意に定まる累積移動距離とする。対象は架空座標なので緯度±90・経度±180を前提にせず、地球上の球面距離に変更しない。

## 初期化と移行

初期データを読み取り確認した結果、椅子500行、位置履歴21,209行、履歴を持つ椅子387台。同じ椅子・同じ `created_at` の重複は初期データにはなかった。

1. `1-schema.sql` に状態テーブルと必要インデックスを定義。
2. `init.sh` で `3-initial-data.sql.gz` 読み込み後に、全椅子の状態行を作成する再構築 SQL を実行。
3. 再構築時だけ、履歴に `LAG` を適用して累積距離を算出し、最新座標と最終日時を格納する。履歴なしの113台にもNULL座標・距離0の行を作る。
4. 既存通知の再構築 `4-notification-data.sql` と合わせ、初期化が全体で成功した場合に通常リクエストを再開する。
5. アプリ再起動では状態行を消さない。再集計は明示した初期化・移行時のみ。

稼働中データへの初回導入は、座標更新を止めて履歴から再構築し、新旧値を照合してから書き込みを再開する。書き込み中の無保護なバックフィルでは、未反映や二重加算が起こり得る。最初の導入では履歴を削除しない。

## 次の段階: coordinate の照会を削減する構成

第1段階の集計テーブル導入を計測した後、必要なら `chair_runtime`（椅子ごとの割当ライド）と `ride_current_status`（ライドごとの現在状態）の導入を検討する。これは位置集計とは別の変更単位とする。

- 配車確定時に `chair_runtime.current_ride_id` を設定し、coordinate で過去ライドを検索しない。
- ステータス更新時に履歴・現在状態・通知イベントを同じトランザクションで更新し、coordinate で毎回ステータス履歴を検索しない。
- 乗車・到着の判定は状態をロックして確認し、同じ到着イベントの二重作成を防ぐ。
- **COMPLETED 作成と、椅子への COMPLETED 通知完了は別。** 現行 matcher は `chair_sent_at` の6件を確認する。`current_ride_id` を評価直後に消して即座に配車可能とすると、完了通知より先に次のライドを割り当てる恐れがある。通知済み判定を、現在の `recordWritten` が確定する進捗と合わせて保持・更新する。
- nearby-chairs の現行条件は「ライドが COMPLETED」、matcher の条件は「通知が完了」。単一の `is_free` に置き換える場合は、この違いを明確に扱う。
- matcher は現在 rides → chairs の順でロックする。runtime を導入する場合は、配車、coordinate、評価、状態変更、通知完了すべてについてロック順と更新責務を再設計する。

この段階は更新経路が多く、初期データからの現在状態・通知進捗の復元も必要。第1段階と同時に一括変更すると効果と不具合の原因を区別しにくい。

## COMMIT の調査と残る確認

初回ログでは DB 全体で191秒の COMMIT があった。その後ユーザーが s1 で取得した実効設定は MySQL 8.0.46、`log_bin=ON`、`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`、バッファプール128MiB、redo容量100MiB、全件スロークエリ記録有効。

ユーザー提供の前後スナップショットは155秒間。Uptime も162→317で、その区間中の再起動は示されていない。

| 指標 | 増分 |
| --- | ---: |
| COMMIT | 19,419回、202.936137秒、平均10.450ms |
| redo ファイル I/O | 56.860539秒（WRITE 6.187130秒、MISC 50.673409秒） |
| binlog ファイル I/O | 23.748088秒（WRITE 0.478701秒、MISC 23.269387秒） |
| redo fsync | 17,756回 |
| 行ロック待ち | 465回、3.371秒 |
| Innodb_log_waits | 0 |

提供された iostat のうち書き込み300回/秒以上の64サンプルでは、書き込み平均約1,044回/秒、`w_await` 平均0.927ms、`%util` 平均76.0%、CPU `%iowait` 平均19.2%。タイムスタンプがなく、初期化を含む実行フェーズとの厳密な対応はできない。CPU負荷も増加しており、ディスク性能上限や COMMIT の全待ち時間を説明できるものではない。MISC は SYNC 以外のファイル操作も含むため、全時間を fsync とみなさない。

ログ同期は有力な原因候補だが、無効化で何ms短縮するかは比較結果で確定する。

- binlog の有効・無効を比較するときはアプリ・スキーマを固定し、設定検査・再起動後に実効値を確認する。redo の永続化設定は1を維持する。
- MySQL 再起動でカウンターがリセットされるので、各条件で前後スナップショットを新しく採取する。初期化や他の負荷が混ざった場合は条件を記録する。
- 提供ログでは `UPDATE ride_statuses SET app_sent_at...` に合計約3秒のロック待ちもある。ライドのロック保持時間と通知更新の競合も確認する。
- 集計ツールを負荷走行と重ねない。設定比較時はログ採取条件を揃える。
- binlog 無効化による複製・時点復元への影響と MySQL 再起動の共有環境への影響を踏まえて比較する。この文書では採用済みとは扱わない。

## 導入する変更の順序

1. **binlog 比較を終えて基準を固定する。** 成功可否、スコア、coordinate の応答時間、COMMIT 平均時間を記録する。
2. **状態テーブル・同期更新・初期再構築・owner/chairs の参照切替を1つの変更にする。** 履歴からの再集計を除去する効果と、coordinate の追加書き込みコストを測る。この段階では近隣検索・配車・ライド状態の読み取り方法を維持する。
3. **近隣検索の最新座標取得を状態テーブルとの JOIN に切り替える。** 現在の空車判定は維持し、既存の相関サブクエリと比較する。効果が小さければ無理に変更しない。
4. **必要なら割当ライド・現在ステータスの保持を別途検討する。** coordinate の残る照会が新しい計測で上位に来る場合に進める。

第2段階の確認例は、初回 `(0,0)` で距離0、次に `(3,4)` で距離7、同じ `(3,4)` の再報告で距離7、`(0,0)` に戻って距離14。移動しない報告でも最終記録日時は更新する。これに並行更新・ロールバック・初期化を加えて、履歴からの再計算と一致することを確認する。

## 実装後の検証と採用条件

1. 初期化直後、全椅子について履歴からの距離・最新座標・最終日時と状態行が一致することを照合する。
2. 初回報告、同一座標、往復、負座標、位置未登録、並行更新、トランザクション失敗・再試行で距離と履歴が一致することを確認する。往復の累積距離を始点と終点の距離に置き換えない。
3. PICKUP / ARRIVED と通知イベントの一体性、アプリ・DB 再起動後の永続性を確認する。
4. `/api/initialize` の再実行で集計値がリセット・復元され、30秒以内に完了することを確認する。
5. manual の座標・累積距離反映猶予3秒を守る。第1段階は同期更新とし、非同期集計の滞留管理を増やさない。
6. 同条件で変更前後を複数回ベンチし、成功可否、スコア、評価502、coordinate の平均・P95、owner/chairs と nearby-chairs の応答時間、COMMIT の回数・平均、書き込み量を比較する。負荷量が増えるので合計時間だけで判断しない。

設計上の狙いは owner/chairs から実行時の `LAG` / `SUM` を除去し、読み取りを履歴件数への依存から椅子台数への依存に変えること。採用は coordinate の追加書き込みコストを含めたベンチ結果で判断する。新テーブルの実装・SQL 実行・デプロイはしておらず、新テーブル導入後の数値は未計測。
